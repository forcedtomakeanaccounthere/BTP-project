# Explainable SYN/UDP Flood Detection in IoT Networks using Lightweight Fuzzy Decision Tree

This project detects SYN and UDP flood behavior in IoT network traffic using
fuzzy membership rules plus supervised tree models. The research workflow is
kept on a laptop; the Raspberry Pi is used for lightweight inference,
monitoring, and a controlled lab response.

## Project layout

- `implementation/shared_preprocessing.py` builds the cleaned, time-ordered
	feature dataset and writes the train/test split.
- `implementation/run_normal_dt.py` trains the plain Decision Tree baseline.
- `implementation/run_fuzzy_dt.py` trains the fuzzy Decision Tree and the
	recommended 300-tree balanced Random Forest.
- `implementation/fuzzy_forest.pkl` is the deployable artifact generated by
	fuzzy training. It contains the model, feature order, fuzzy membership
	parameters, training quantile bounds, thresholds, and rolling window size.
- `implementation/fuzzy_inference.py` loads that artifact and performs the
	same transformations during inference.
- `implementation/live_detector.py` replays a CSV in bounded windows and
	writes structured JSON Lines events for Pi testing.
- `implementation/monitor_dashboard.py` serves a dependency-free monitoring
	page that displays packet volume, model probability, fuzzy confidence,
	threshold, source, and action.

The existing notebooks remain useful for exploratory analysis and figures.
The command-line scripts are the reproducible path for training and deployment.

## Laptop: train and export

From the repository root, create an environment and install dependencies:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
cd implementation
python shared_preprocessing.py
python run_normal_dt.py
python run_fuzzy_dt.py
```

The fuzzy command writes `fuzzy_forest.pkl` and updates
`fuzzy_dt_results.json`. Do not retrain this GridSearch/Random Forest workflow
on the Pi. Copy the artifact and the inference/monitor scripts to the Pi after
training. Only load artifacts you created or trust: joblib/pickle files can
execute code when loaded.

## Raspberry Pi: replay test

Replay the cleaned dataset first so the complete detection path can be checked
without generating traffic:

```bash
cd implementation
python3 live_detector.py \
	--replay-csv syn_udp_flood_attack_data_clean.csv \
	--artifact fuzzy_forest.pkl \
	--log monitor_events.jsonl \
	--delay 0.05
```

In another terminal, expose the dashboard:

```bash
python3 monitor_dashboard.py --log monitor_events.jsonl --port 8080
```

Open `http://<raspberry-pi-ip>:8080`. The dashboard refreshes once per second.
The event stream is intentionally simple JSONL so it can later be forwarded to
MQTT, SQLite, or another observability system without changing inference.

## Detection and response states

Each rolling window produces:

1. `ALLOW` when the combined score is below 75% of the tuned threshold.
2. `RESTRICT` when traffic is suspicious but has not crossed the threshold.
3. `BLOCK` when the score crosses the exported threshold.

The current monitor records the action; it does not install firewall rules.
That is deliberate for SSH safety and repeatable demonstrations. A future
firewall adapter should use an allowlist, a temporary timeout, explicit lab
mode, and a dry-run default. Never block the management IP while connected over
SSH.

## Controlled live testing

The existing `simulating_Attack.py` contains hard-coded addresses and a high
packet count. Treat it as historical research code, not a Pi test command.
For the lab demonstration, first verify packet capture, feature windows,
artifact inference, and dashboard events in that order. Then use a bounded,
authorized test source and a target-only network. Record the source address,
model score, threshold, action transition, and recovery/removal event.

## Limitations and next work

`live_detector.py` currently provides a CSV replay path so the laptop and Pi
can be validated deterministically. The next adapter can translate captured
Scapy/tcpdump packet metadata into the same six-column packet records
(`Time`, `Length`, `Info`, `Protocol`, `Source`, `Destination`) and feed the
same rolling feature window. This keeps packet capture separate from model
logic and makes the dashboard usable for both replay and live sessions.

This is a research prototype, not a complete network firewall. Validate false
positives, recovery behavior, and the selected threshold on traffic from the
actual IoT lab before enabling any blocking action.
